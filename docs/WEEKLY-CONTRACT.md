### 0.1 Repo facts that shape the design (verified by the Lead)

- `public/data/latest.json` contains **only the current week's records**. `history()` in
  `src/data.js` therefore returns ~1 point per series and `cell().delta` is almost always `null`.
  The real multi-week evidence already exists in **34 snapshots** under `data/history/*.json`
  (ISO weeks `2026-09-07` … `2026-10-05`) and is currently **published to nobody**.
  R4 is therefore impossible without publishing an aggregated weekly history artifact (§3).
- `config/sources.json` carries no display/battery data. Screen size and battery must come from
  a new, researched `public/data/specs.json` (§5).
- Older snapshots stamp `week` with the *collection date* (e.g. `2026-09-20`), not an ISO week
  start. Any aggregation **must** normalize with `weekStart(record.week)`.
- Snapshots contain `missing`/`invalid` carried rows. Those are **not** real observations of that
  week and must never become trend points.
- The site UI is Chinese; code identifiers and docs are English. Keep both conventions.
- **Anti-fabrication is the project's cardinal rule** (README, docs/PLAN.md §6): no price without
  `sourceId` + `sourceUrl` + `collectedAt` + `rawEvidence`; missing data renders blank/`暂无数据`;
  gaps stay gaps (`connectNulls: false`); never interpolate; never guess.

## 2. C2 — Published weekly history artifact (R4 enabler)

**New file `public/data/history.json`**, generated by **new `scripts/history.mjs`**:

```json
{
  "apiVersion": "1.1",
  "generatedAt": "2026-10-10T10:21:42.373Z",
  "weeks": ["2026-09-07", "2026-09-14"],
  "points": [
    {
      "country": "sa", "brand": "samsung", "series": "Galaxy A",
      "model": "A57 5G", "channel": "official", "variant": "256GB",
      "week": "2026-10-05", "price": 2499, "currency": "SAR", "priceUsd": 666.4,
      "state": "live", "sourceId": "samsung-sa-a-official",
      "sourceUrl": "https://…", "collectedAt": "2026-10-10T10:14:05.569Z",
      "effectiveDate": "2026-10-10"
    }
  ]
}
```

Rules for `scripts/history.mjs` (reads every `data/history/*.json`):
1. Normalize `week` to the ISO Monday week start (`weekStart(record.week)`).
2. Keep only **real observations**: finite `price` > 0 **and** `state ∈ {live, promo}`.
   Carried `missing`/`invalid`/`unavailable` rows are dropped.
3. Dedupe per `(country, model, channel, variant, week)`: prefer newest `collectedAt`; tie → lowest price.
4. Deterministic order; `weeks` = sorted distinct weeks; never invent a point or a week.
5. Non-fatal: a malformed snapshot is skipped with a warning; the script never invents data.
6. It runs in `collect.yml` and is committed with the rest of the data.
7. **`brand` and `series` are copied verbatim from the source record** — they are real collected
   fields, never inferred. A legacy row with an empty brand stays `null`.
   *Why (Lead ruling, after the UI thread found it):* `brand`/`series` are trend scope filters, and
   `models.json` only knows currently-listed ids. Without these fields every historical point from a
   retired id (`A06`, `A57`) fails a brand filter, which left only 2 matched series and collapsed the
   trend to `样本不足` whenever the user selected the only brand. Comparison stays case-insensitive
   (`Samsung` in older snapshots vs `samsung` today), so no normalization is needed at write time.

`scripts/validate.mjs` gains a strict `public/data/history.json` check: `apiVersion === "1.1"`,
`weeks` sorted ISO dates, every point's `week` ∈ `weeks`, `price` finite > 0,
`state ∈ {live, promo}`, `sourceId`/`sourceUrl`/`collectedAt` present, week === ISO week start of
its own `week` value, and one point per `(country, model, channel, variant, week)`.

### 3.1 Weekly history is merged into the client
`history(country, model, channel, variant, until)` must return **one point per ISO week** built from
`latest.json` records **plus** `history.json` points, so trend charts and week-over-week deltas are
real. Dedupe by `(country, model, channel, variant, week)`; a `latest.json` record wins for the
current week. `cell()` deltas must come from two real adjacent ISO weeks, otherwise `null`
(never a carried row, never an interpolation). All existing `cell`/`history` semantics otherwise
stay as they are.

**Lead addendum — displayed USD is derived from the PUBLISHED rate (found on the merged upstream
data).** `priceUsd` is a *function*, documented as `round(price × fx.rates[currency], 2)` with the
rates in the published `fx.json`; `validate.mjs` enforces exactly that for `latest.json`. Points in
`history.json` are historical evidence and keep the `priceUsd` computed at their own collection
time, so after an FX refresh they can disagree with the current rate (real case: three TRY points
from the 2026-10-09 snapshot rendered `$270.25` where the published rate gives `$269.69`, failing
`tests/matrix.spec.js`'s displayed-USD invariant). Therefore, at the end of `hydrate()`, the client
must normalise `priceUsd` for both `records` and `historyPoints` from the published rates: when a
finite rate exists for the row's currency and the row has a finite `price`, set
`priceUsd = round(price × rate, 2)`; when no rate exists, leave the stored value untouched (real
published data is already `null` there, and fixture data must not be nulled). Do not rewrite
`history.json` on disk and do not change `weeklyTrend`, which compares local prices within a
currency.

### 3.2 `weeklyTrend(scope)` — the frozen aggregation
`scope = { country, brand, series, channel, variant, screenInches, batteryMah, storage, until, limit }`
(absent/`ALL` means unrestricted; `until` defaults to the latest week; `limit` defaults to 12).

Definitions (these are the contract — the UI and the reviewer test against them):
- A **series** is `(country, model, channel, variant)`. `variant: ALL` collapses variants by taking
  the lowest real price per week.
- `matched(w)` = series having a **real** point in both `w` and the immediately preceding week in
  the data, within scope. `pct = (p_w − p_{w−1}) / p_{w−1}`.
- `medianPct(w)` = median of `matched(w)`, but **`null` when `matched(w).length < 3`**
  (too thin to be a trend — this is a gap, never a guess).
- `index` = base **100** at the first week with a non-null `medianPct`, then chained
  `index(w) = index(previous non-null) × (1 + medianPct(w))`. Gaps stay `null`.
- `changedUp` / `changedDown` = count of `pct > +0.5%` / `pct < −0.5%`; the rest are flat.
- Return shape:
```js
{
  weeks: ["2026-09-14", …],
  points: [{ week, index, medianPct, changedUp, changedDown, sample }],
  summary: {
    seriesCount, sample, up, down, flat, medianPct,
    topGainers: [{ country, model, variant, channel, from, to, pct }],  // up to 3
    topLosers:  [ … ],                                                // up to 3
    suspects:   [{ country, model, variant, channel, week, from, to, pct }], // see §3.3 A2
    markets:    [{ id, sample }],   // matched-series contribution per market  (A3)
    channels:   [{ id, sample }],   // matched-series contribution per channel (A3)
    insufficient: boolean,   // true when fewer than 2 weeks have a non-null medianPct
  },
  excluded: { missingSpec: 0, noSpec: 0 }
}
```
- Must not touch `window`/`import.meta.env` at module scope (Playwright imports this file in plain
  Node — existing constraint).
- `excluded.missingSpec` counts in-scope models dropped because an active spec filter
  (screen/battery/storage) has no value for them; `excluded.noSpec` counts models with no spec entry.

### 3.3 Amendment A1–A3 — Lead ruling (verified against all 34 snapshots)

Evidence the Lead reproduced independently: the merged snapshots yield **5 ISO weeks,
138 real points**, but only **one market has adjacent-week comparables — Saudi retail**:
`sa|A57|retail|256GB`, `sa|A16|retail|128GB`, `sa|A06|retail|128GB`, `sa|A57 5G|retail|256GB`
(matched = 3, 4, 4, 4 for weeks 2026-09-14 → 2026-10-05). `A57` and `A06` are **historical ids
present in the snapshots but absent from `models.json`**.

- **A1 — scope.** `weeklyTrend(scope)` operates over **all real weekly points in the merged
  history**, and is **NOT** restricted to `models.json` ids. Caller filters narrow the scope only
  when explicitly set. The UI must state the trend scope and sample size. (Without A1, strict
  `models.json` scoping leaves 2 matched series per week, i.e. no trend line at all — R4 would be
  unmeetable.)
- **A2 — suspect moves: visible, never deleted.** `summary.suspects` lists matched series with
  `|pct| > 0.5` (>50% week-over-week). They **stay in the median** (no silent deletion), and the
  analysis summary must name them as `疑似异常，需核对来源` when non-empty. Rationale: the real data
  contains `sa|A06|retail|128GB` at −99.3% then **+11731.8%**, and `sa|A16|retail|128GB` at −66.2%,
  which are almost certainly parse artifacts. Hiding them would be dishonest; letting them drive an
  unlabelled narrative would be worse.
- **A3 — thin-sample honesty.** When the latest week's matched sample is `< 3`, the section must say
  `本周可比样本不足`. When the comparable sample is concentrated in one market/channel, the section
  must name it (e.g. `样本仅来自沙特阿拉伯 · 零售渠道`).

These amendments relax nothing in §7 (anti-fabrication). They only make the thin reality explicit.

### 3.4 Lead rulings on PLAN-WEEKLY §8 (final — implement these)

- **A2 threshold is the FRACTION form.** `|pct| > 0.5` means **>50% week-over-week**.
  (`0.005`, i.e. ±0.5%, remains the up/down bucket boundary in §3.2 — do not conflate the two.)
  On current data only 3 moves qualify as suspects.
- **OQ-1 — `until`.** `weeklyTrend` defaults to the week currently selected in the 周次 picker, and
  the section is labelled with that week, so the trend agrees with the matrix.
- **OQ-3 — carried points (correction).** `history()` KEEPS its existing behaviour: a carried
  (`missing`/`invalid`) row that has a price is returned **with that price** and `carried: true`
  (the detail chart marks it with a hollow dot; the record list shows `缺价 · 沿用`). Do **not**
  null it — that would delete verified information the product deliberately preserves.
  What changes is the *delta*: `cell().delta`/`percent` are computed **only when the current and the
  immediately preceding priced point are both real** (`live`/`promo`); otherwise `null`.
  `weeklyTrend` uses real points only.
- **OQ-4 — channels.** No channel collapse; scope fields are filters.
  (`variant: ALL` keeps the existing lowest-real-price-per-week collapse from §3.2.)
- **OQ-5 — week extent.** `weeks` and `points` cover the same week list, starting at the first week
  that has a computable median (current data: `2026-09-14`).
- **OQ-6 — variant vs storage.** `variant` filters the record's variant; `storage` matches
  `specs.storage` and only affects spec-coverage exclusion (`excluded.missingSpec`).
- **Merge precedence (pins §3.1).** Per `(country, model, channel, variant, week)`: a **real**
  observation always beats a carried row. Among real points the current week prefers `latest.json`;
  otherwise newest `collectedAt`, then lowest price. A carried row may fill only a week that has no
  real point, and never feeds a delta or a trend point.
- **Baseline caution.** The pinned first-run baseline in PLAN-WEEKLY §5 is a *derived* expectation.
  The integrator and reviewer must derive the numbers from the implementation; a mismatch is a
  question for the Lead, not an automatic FAIL.

## 7. Anti-fabrication (hard rules — apply to every thread)

1. No price or spec value without a real, recorded source.
2. No interpolation; a gap is a gap (`connectNulls: false`).
3. Carried/carried-over values stay visibly marked (`缺价 · 沿用`) and never seed a trend point.
4. Missing data renders blank / `暂无数据` / an explicit note — never a placeholder number.
5. Nothing in `src/` or the data may be hardcoded per country/model except config.
